# Pitfalls Research

**Domain:** local gameplay highlight clipper CLI (audio/motion action detection, ffmpeg render, optional Whisper/Ollama)
**Researched:** 2026-11-12
**Confidence:** MEDIUM. Date, licence and wheel facts were checked live (PyPI JSON, web search). Detection/ffmpeg behaviour is from established practice and the ffmpeg docs, not re-tested here. Items marked [VERIFY] need a 5-minute check on a real file.

Phase key: 01 core, 02 video, 03 speech/facecam, 04 vision/readme, L = launch.

## Critical Pitfalls

### P1: Constant-loud games and music make the audio signal flat or inverted
**What goes wrong:** GTA has a radio and score under everything. Absolute RMS is high all the time, so "loud" picks nothing or picks the radio chorus. Quiet-game footage gets zero peaks.
**Why it happens:** Global normalisation (max or percentile over the whole file) with energy as the only feature.
**How to avoid:** Score deviation from a rolling baseline (median and MAD over about 60-120 s), not absolute level. Use spectral flux/onsets and broadband transients (explosions, gunfire, crashes) rather than sustained RMS. Optionally high-pass at about 150 Hz so bass-heavy music does not dominate. Fall back to visual weight when audio variance is tiny (flag it in report.json). Weights live in the config file (already planned).
**Warning signs:** Top-N windows clustered in one song section; audio score std-dev near zero; all clips sound the same.
**Phase:** 01 (baseline design), 02 (visual fallback). Add a synthetic case: constant music bed + bursts, bursts must still win.

### P2: Variable-frame-rate (VFR) recordings break seeks, sync and timestamps
**What goes wrong:** OBS and many capture tools can write VFR or drop frames. The 5 fps proxy index-to-time mapping drifts, so the clip lands seconds from the detected peak, or audio and video desync after `-ss`.
**Why it happens:** Computing time as frame_index/fps instead of using real PTS. OBS stamps by wall-clock when frames are missed. ffmpeg's `-ss` behaviour differs before vs after `-i`. [VERIFY on a real OBS file]
**How to avoid:** Derive every timestamp from PTS (`ffprobe -show_entries frame=pts_time`, or build the proxy with `-vf fps=5` so the proxy is constant-rate by construction; use `-fps_mode cfr`, which replaces the old `-vsync`). Keep audio analysis on the same time base (`-ar 16000 -ac 1` from the original). In render use input-side `-ss` (fast, accurate on re-encode since we always re-encode) and never `-c copy`. Add a VFR fixture to the synthetic generator (alternating 24/60 fps segments) and assert peak time within +-0.25 s.
**Warning signs:** `r_frame_rate` != `avg_frame_rate` in ffprobe; drift that grows through the file; clips that start in the wrong place only on OBS files.
**Phase:** 01 (probe + proxy), 02 (render sync).

### P3: Picking ten clips of the same moment
**What goes wrong:** A 90 s firefight yields eight overlapping windows. Report looks fine, output is useless.
**Why it happens:** Top-N on a smoothed score without suppression.
**How to avoid:** Greedy non-maximum suppression: after selecting a peak, exclude +-(max_len) around it (or any window overlapping a chosen one by more than 20%). Also enforce a minimum gap between peak centres (default 30 s) and spread across the timeline. If fewer than N survive, return fewer, do not pad.
**Phase:** 01 (peak picking test with a dense burst cluster).

### P4: Long VOD drift and memory blow-ups
**What goes wrong:** Whole-file normalisation lets one huge explosion flatten the rest of a 10-hour file. Loading the full decoded audio (10 h x 16 kHz float32 is about 2.3 GB; float64 double that) or all proxy frames into numpy kills 8 GB laptops.
**Why it happens:** `np.fromfile` / `librosa.load` of everything; list of frames.
**How to avoid:** Stream audio from ffmpeg stdout in chunks (e.g. 60 s), compute per-0.5 s features incrementally and keep only the feature arrays (about 72k floats per hour at 0.5 s). Same for video: read proxy frames from a pipe (`-f rawvideo -pix_fmt gray`, 320 px, 5 fps), keep only the previous frame. Normalise with robust rolling percentiles (or per-30-min segment), never global max. Cap proxy ffmpeg with `-threads` so the CPU is not pegged.
**Warning signs:** RSS grows linearly with duration; late-file scores always low.
**Phase:** 01 (audio), 02 (video). Add a 3 h synthetic memory test (generated by looping features, not a real file).

### P5: Variable-geometry sources: HEVC, 10-bit, HDR, 4K
**What goes wrong:** PS5/Xbox captures can be HEVC, 10-bit, HDR (BT.2020/PQ). Re-encoding to H.264 8-bit without tone-mapping gives washed-out grey clips. OpenCV may fail to decode HEVC or hardware-only profiles, or decode slowly at 4K. [VERIFY: PS5 can save 4K HDR clips; HDR video capture is a setting, default format is WebM-ish/MP4 depending on firmware]
**Why it happens:** Assuming SDR 1080p H.264, and using OpenCV VideoCapture on the original.
**How to avoid:** Probe `pix_fmt`, `color_transfer` (`smpte2084` or `arib-std-b67` = HDR), `color_primaries`. Do all analysis through ffmpeg-produced proxies (decode once, scale to 320 px early with `-vf scale=320:-2` so 4K decode cost is the only cost; add `-hwaccel auto` only as an optional speedup, never required). For HDR render, apply tone-mapping (`zscale=t=linear:npl=100,format=gbrpf32le,zscale=p=bt709,tonemap=hable,zscale=t=bt709:m=bt709:r=tv,format=yuv420p`; needs ffmpeg built with libzimg, else fall back to `tonemapx`/`colorspace` and print a warning). Always output `-pix_fmt yuv420p`, tag bt709. Warn, do not crash, when HDR is detected and tone-mapping is unavailable.
**Warning signs:** Output looks desaturated; `Unsupported` decode errors; analysis of a 4K file takes minutes longer than 1080p.
**Phase:** 01 (probe flags + warnings), 02 (render tone-map). Test with a synthetic HDR-tagged file (`-color_trc smpte2084 -pix_fmt yuv420p10le`).

### P6: ffmpeg missing, old, or without libass/libx264
**What goes wrong:** Caption burn-in via the `ass`/`subtitles` filter fails with "No such filter" on builds without libass (some minimal static or distro builds). Older ffmpeg lacks `-fps_mode`. A user has ffmpeg 4.x from apt.
**Why it happens:** Only checking `which ffmpeg`.
**How to avoid:** At start run `ffmpeg -hide_banner -filters` and `-encoders`, assert `ass`, `libx264`, `aac`; check version at least 5.0 (for `-fps_mode`). On failure print platform install help (brew install ffmpeg / winget install Gyan.FFmpeg / apt install ffmpeg) and exit 3. If only libass is missing, degrade: write the .ass next to the clip and render uncaptioned with a clear message, do not crash mid-run after 20 minutes of analysis.
**Warning signs:** Failure appears only at render of the first captioned clip.
**Phase:** 01 (preflight check), 03 (caption fallback).

### P7: Captions covering the HUD, drifting, or cutting mid-sentence
**What goes wrong:** Centre-bottom captions sit on GTA's minimap/ammo/wanted stars area; ASS timing is off because transcription ran on the full file but clip times are relative; clip cut mid-word.
**Why it happens:** Whisper timestamps are in source time; ASS needs clip-relative time. Default caption position is bottom. Word timestamps from the VAD-trimmed audio are offset.
**How to avoid:** Subtract clip start from every word time and clamp. In 9:16 the HUD corners are cropped away partly, so place captions at about 62-70% height (above the bottom third, below the action centre), safe margins 8% sides. Run Whisper only on the clip segments (not the whole VOD) so cost is bounded and time offsets are simple. Extend/snap clip bounds to the nearest silence or word boundary (do not cut inside a word: if a word spans the boundary, move the boundary to its end). Render with the same `-ss` basis as the ASS (apply the `ass` filter before seeking is wrong; use filter after trimming, or offset events).
**Warning signs:** Captions lead or lag growing through a clip; text overlapping the minimap at the bottom-left.
**Phase:** 03 (captions). Test: synthetic speech (TTS-free: pre-recorded WAV fixture) with known word times.

### P8: Action-following crop jitters or loses the subject
**What goes wrong:** Centre-of-motion jumps with camera turns, HUD flashes and screen shake; the crop window shakes like a handheld camera, or follows the HUD/minimap.
**Why it happens:** Using raw frame-difference centroid per frame; including the static HUD in the motion mask; no smoothing or deadband.
**How to avoid:** Mask out the outer 12% and the known HUD corners; estimate motion on low-res gray with global-motion compensation or use the median of the top-k motion blocks; smooth with a critically damped filter or Savitzky-Golay over about 1.5 s; add a deadband (move only if target is more than 8% of crop width from the crop centre); limit pan speed. Fall back to centre crop whenever confidence is low or motion is global (camera turn = most pixels move). Default to the centred crop where the game's reticle/player normally is (third-person GTA keeps the player near centre).
**Phase:** 02. Metric: max crop-x acceleration test on the synthetic video.

### P9: False positives from menus, loading screens, overlays and alerts
**What goes wrong:** Pause menu, map zoom, loading/cutscene fades, and stream overlays (alerts, chat popups, donation sounds) show high motion or loud audio.
**Why it happens:** Motion = any pixel change; audio = any loud sound including alert chimes and TTS donations.
**How to avoid:** Penalise full-frame near-uniform transitions (fades and loading screens: low edge density, mean luma slope) and very low audio-visual agreement. Require agreement between at least two signals for a top-tier score (audio burst + visual change within +-1 s). Down-weight windows that are speech-only loud (high 300-3400 Hz voice band share, no low-frequency transient). Expose `--ignore START-END` ranges later; document known limits in the README rather than over-claiming. Do not try to detect specific overlays at launch.
**Warning signs:** Top clips are menus/loading; clips start with a spinner.
**Phase:** 02 (agreement rule, fade detection); 04 (vision re-rank is the safety net).

### P10: Clips that start at the peak or end mid-action
**What goes wrong:** The highlight is the explosion, but the clip begins on the explosion frame and ends 2 s later; viewers get no setup or aftermath.
**Why it happens:** Window anchored on the peak sample.
**How to avoid:** 60/40 split (already in plan) measured from the peak onset, not the peak maximum; snap start backwards to the nearest quiet point or cut within +-2 s, snap end to the decay (score < 30% of peak) plus 1.5 s tail; clamp to --min/--max after snapping. Add fades only after the snap (0.3 s fades must not eat the first beat).
**Phase:** 01 (windowing), 02 (cut snap).

### P11: Facecam misdetection
**What goes wrong:** Haar/DNN face detector fires on in-game characters, NPCs, or posters; "static corner region" is actually the minimap or a webcam-less HUD; stacking duplicates gameplay and shrinks it.
**Why it happens:** Single-frame detection; no temporal stability check; PS5/Xbox captures have no facecam at all.
**How to avoid:** Require a rectangle that is static (very low temporal variance) across at least 30 sampled frames over the whole file, rectangular with edges, in a corner, and with a face in at least 50% of those samples. Default `--facecam auto` to "off" unless confidence is above threshold; print what was decided in report.json. Never crop with a guessed region without that evidence.
**Warning signs:** Facecam found on console captures; box moves between runs.
**Phase:** 03.

### P12: Audio desync after trimming and codec/container surprises
**What goes wrong:** mkv with Opus audio breaks AAC-only assumptions; long mkv without a cue index seeks slowly or inaccurately; OBS recordings that were stopped abnormally have no duration/index; multiple audio tracks (game vs mic) pick the wrong one.
**Why it happens:** Assuming one AAC track and a clean container.
**How to avoid:** Probe all audio streams; default to the first, offer `--audio-track N`, and analyse a mix when several (document it). Always re-encode audio to AAC at render (`-c:a aac`), so Opus/FLAC input is fine. For truncated or unindexed files, ffprobe duration may be N/A: compute from the last packet (`-show_entries packet=pts_time -read_intervals`), and accept slower input-side seek. Prefer `-ss` before `-i` plus `-accurate_seek` (default on re-encode) and `-avoid_negative_ts make_zero`. Suggest `ffmpeg -i in.mkv -c copy out.mp4` remux in the error text for broken indexes.
**Warning signs:** `Duration: N/A`; render takes minutes for a late clip; first frames of the clip black.
**Phase:** 01 (probe), 02 (render).

## Moderate Pitfalls

### P13: Python/wheel and environment surprises
**What goes wrong:** Python 3.13/3.14 or Intel macOS or ARM Windows lack wheels for a dependency, so `uvx clip-anything` compiles from source and fails.
**Checked (PyPI, 2026-11-12):** ctranslate2 4.9.0 ships cp313 and cp314 wheels (MIT, requires >=3.9); faster-whisper 1.2.1 is pure Python (MIT, >=3.9); opencv-python-headless 5.0.0.93 ships abi3 wheels (cp37-abi3) for macOS arm64/x86_64 and Windows; PyAV 19.0.2 requires Python >=3.12 (older av is used on 3.11 by the resolver, [VERIFY]).
**Prevention:** Note opencv is now 5.x, a new major: pin `opencv-python-headless>=4.9,<6` and test on the resolved version, since defaults changed between majors. Make faster-whisper an extra (`clip-anything[speech]`) so the core install is only numpy/scipy/opencv/rich; core must work with no Whisper installed. Add CI matrix 3.11/3.12/3.13 on macOS and Windows (GitHub Actions) if time allows; otherwise at least `uv pip install --dry-run` on 3.13. Avoid librosa and torch at launch (librosa pulls numba/llvmlite; slow import and wheel lag); use scipy for STFT and flux.
**Phase:** 01 (pyproject), L (clean-machine install test with `uvx`).

### P14: Whisper model download inside a CLI
**What goes wrong:** First captioned run silently downloads 150 MB-1.5 GB from Hugging Face, looks hung, fails offline, breaks the "no network" promise.
**Prevention:** Never download implicitly. Detect missing model and either skip captions with one clear line, or ask once (`--download-model base.en` or an interactive y/N when stdin is a TTY, never in `--json`). Default model `base.en`/`small.en` (CPU int8). Document the download as the one explicit network step and where the cache lives (HF cache dir). Pass `local_files_only=True` unless the user opted in.
**Phase:** 03.

### P15: Windows paths, quoting and temp files
**What goes wrong:** Paths with spaces or non-ASCII, and the `ass=`/`subtitles=` filter, which needs `C\:/path` escaping (colon and backslash); shell=True quoting; temp files left in `%TEMP%`; `\\?\` long paths.
**Prevention:** Use `subprocess.run([...list...])`, never shell=True; for subtitles filter, copy the .ass into the working temp dir with a safe name (`caps.ass`) and run ffmpeg with `cwd` set there so the filter argument is a bare filename. Use `pathlib`. Put temp in a `tempfile.TemporaryDirectory` inside the output dir (or `--tmp`), cleaned in `finally`; delete the intermediate proxy files. Write the final file to `name.tmp.mp4` then rename so a crash never leaves a half clip that looks valid. Check free disk space before render (clips x estimated size). No Windows machine is available, so add a unit test for the filter-path escaper and list Windows as "best effort" in README.
**Phase:** 01 (temp handling, subprocess), 03 (ASS path).

### P16: Parallel renders saturate CPU or disk
**What goes wrong:** Ten x264 jobs at once on a laptop thrash and thermal-throttle; the machine becomes unusable.
**Prevention:** Render sequentially by default; `--jobs` optional, capped at cores/2, and set `-threads` per job. Use `-preset veryfast -crf 20` (already planned). Show progress per clip. Document that hardware encoders (VideoToolbox/NVENC) are not default because quality-per-bit and portability are worse.
**Phase:** 01 (render).

### P17: Slow full-res decode and re-decode per signal
**What goes wrong:** Decoding the original for audio, again for motion, again for scene cuts, again per clip multiplies runtime on 4K HEVC.
**Prevention:** One ffmpeg pass can emit both the audio pipe and the proxy (two outputs from one input with `-map`). Cache the proxy features by (path, size, mtime) hash in the temp or `.clip-anything-cache` dir so re-runs with different `--count` are instant. Report timings in the progress UI so slowness is visible.
**Phase:** 01 and 02.

### P18: Scoring that cannot be tuned or explained
**What goes wrong:** Hard-coded weights; after launch nobody can fix GTA 6 results without a code change.
**Prevention:** report.json includes each signal's normalised score per clip and the weights used; `--config` loads weights; keep defaults conservative. Tune on real GTA 5 footage, not just the synthetic video; the synthetic test proves plumbing, not taste.
**Phase:** 01 (report), 04 (document tuning in README).

### P19: Scene-cut false positives in games
**What goes wrong:** Histogram-delta cuts fire on muzzle flash, explosions, camera whips and fades, so "cut" cannot mean editorial cut.
**Prevention:** Treat scene cuts as a snapping aid and a low-weight feature, not as a highlight signal; require a persisted change (post-cut frames similar to each other). pyscenedetect is not in the dependency list; do not add it for launch (BSD, but extra weight).
**Phase:** 02.

## Minor Pitfalls

### P20: Ollama vision step surprises
**What goes wrong:** Ollama present but no vision model pulled, or slow; requests hang; JSON parse fails.
**Prevention:** Short connect timeout to 127.0.0.1:11434, `GET /api/tags` to check the model exists, per-call timeout, tolerant parsing, fall back silently to the existing score. Never auto-pull a model. Sample 3 frames per candidate, not the clip.
**Phase:** 04.

### P21: UI and naming
**What goes wrong:** Rich progress corrupts `--json` stdout; re-runs overwrite clips from another video.
**Prevention:** Progress to stderr, JSON to stdout, ASCII fallback; name `<stem>_01_<mm-ss>.mp4`, no overwrite without `--force`.
**Phase:** 01.

### L3: Trademark: "GTA" in marketing
**What goes wrong:** Product name, logo or tagline implying affiliation (e.g. "GTA Clipper"), using Rockstar/Take-Two logos or key art, or domain/handle with the mark. Take-Two enforces actively (it has taken down mods, leaks and fan projects).
**Prevention:** Nominative use only, plain text: "works great on GTA 5 / GTA 6 gameplay recordings"; no logos, art, or screenshots with Rockstar branding in the repo; product name stays Clip Anything; add the standard disclaimer ("Not affiliated with or endorsed by Rockstar Games or Take-Two Interactive. Grand Theft Auto is a trademark of Take-Two."). Do not put GTA in the package name, repo name, PyPI keywords-heavy spam, or the domain. Sample assets: synthetic only (matches the GRAPH rule). Not legal advice; the owner's legal-suite skills can do the launch review.
**Phase:** L, 04 (README).

### L4: Sharing game footage: copyright/ToS
**What goes wrong:** Users or the launch demo post raw game footage. Publishers generally permit gameplay video under their content policies, but terms vary and Rockstar/Take-Two's policy on pre-release or leaked footage is stricter. [VERIFY current Rockstar/Take-Two policy page before launch]. Day-one footage may include spoilers; embargo and platform rules may apply.
**Prevention:** Tool is local and never uploads, so it holds no footage. README note: "you are responsible for rights to footage you clip and post; check the publisher's content policy and platform rules; music in clips (radio) can trigger Content ID claims". Demo video: use own gameplay, short, no leaked material; consider muting licensed radio in demos. Do not bundle any game footage in the repo.
**Phase:** L.

### L5: Dependency licences
**Checked (PyPI metadata live, 2026-11-12):** ctranslate2 4.9.0 = MIT; faster-whisper 1.2.1 = MIT; opencv-python-headless 5.0.0.93 = Apache-2.0 (the wheel also bundles FFmpeg, which is LGPL, so note it in NOTICE). OpenAI Whisper weights = MIT (OpenAI repo; Systran converted models on HF are MIT [VERIFY model card per model]). numpy/scipy BSD; rich/typer MIT. librosa (ISC) and pyscenedetect (BSD-3) are not dependencies; if added, still compatible.
**Real licence risks:** (1) ffmpeg is an external binary the user installs, so we are not redistributing it. Never bundle it (GPL builds with libx264 would force GPL obligations on the bundle). (2) Ollama and its vision models have their own licences (e.g. Llama community licence); we only call a local HTTP API and never download or ship them. (3) `libx264` encoding is GPL-component software but invoked as a separate process; fine.
**Prevention:** Add a THIRD_PARTY.md or NOTICE with the above and a line in README. Run `pip-licenses` once before tag.
**Phase:** L/04.

### L6: Launch-week process risks
**What goes wrong:** PyPI name publish fails (trusted publishing not configured; Mock Anything hit npm 404s the same way); `uvx clip-anything` untested on a clean machine; README demo GIF shows a result the shipped version cannot reproduce; ship day collides with the Sunday midnight schedule.
**Prevention:** Test-publish to TestPyPI on Friday; Saturday night run `uvx --from dist/*.whl clip-anything` in a fresh venv with ffmpeg removed from PATH (expect exit 3 with help text) and with it present; record the demo from the tagged commit. Fall back to a GitHub release with the wheel if PyPI trusted publishing is not ready. Also update shipatmidnight.dev same day (owner standing rule).
**Phase:** L.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Global max normalisation | 5 lines | Fails on long VODs and constant-loud games (P1, P4) | Never; rolling percentile is as short |
| `time = frame_idx / fps` | Simple | VFR drift (P2) | Never; derive from PTS or constant-rate proxy |
| Centre crop only | Zero jitter | Misses the action off-centre | Acceptable for day-one render (step 3); step 6 adds follow |
| Whisper on the whole VOD | One call | Hours of CPU, GBs | Never; transcribe selected windows only |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Full audio into numpy | RSS GBs, swap | Streamed chunks (P4) | About 3 h and up at float32 on 8 GB |
| OpenCV decode of 4K HEVC | Minutes per hour of footage | ffmpeg scale to 320 px at decode | Any 4K input |
| Decoding once per signal | 3x runtime | Single ffmpeg, two outputs (P17) | 1 h+ files |
| Parallel x264 | Fan noise, UI freeze | Sequential default (P16) | `--count` 10+ |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Passing user paths to a shell | Command injection through filenames | Argument lists, no shell=True |
| Writing to arbitrary `--out` | Overwrite user files | Refuse non-empty existing files without `--force` |

## "Looks Done But Isn't" Checklist

- [ ] **Peak picking:** passes on synthetic, but test a constant-music-bed variant and a dense cluster (P1, P3).
- [ ] **Render:** plays in VLC; also check it plays in QuickTime and a phone (yuv420p, +faststart, even dimensions).
- [ ] **Captions:** words align at the END of a clip, not only the start (drift check).
- [ ] **VFR:** an OBS-style file (not just testsrc CFR) was analysed and peaks land within 0.25 s.
- [ ] **HDR/10-bit:** tagged file produces non-grey output or a printed warning.
- [ ] **No ffmpeg / no libass / no Whisper:** each yields a clear message, correct exit code, no traceback.
- [ ] **Install:** `uvx clip-anything --help` on a clean machine and Python 3.13.
- [ ] **Real footage:** at least one real GTA 5 recording reviewed by eye, top 5 clips judged good.
